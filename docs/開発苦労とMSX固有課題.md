# 開発苦労と MSX 固有の課題

本書は「零の咆哮 改」開発で踏んだ罠・MSX/V9938/SDCC 固有の問題とその解決策をまとめる。
さらに **§B** に、旧版「零の咆哮」（cport）から移植した部分について、旧版制作時にも苦労した
とされる知見（移植にあたり写したもの）を収録する。構造は [設計書.md](設計書.md)、仕様は
[仕様書.md](仕様書.md) を参照。

---

## A. 本作（新版）で踏んだ罠と対策

### A-1. ビルドシステム（最悪級）
- **ヘッダ依存欠落による stale-object バグ**：`Entity` 構造体にフィールドを追加した後、増分
  `make` がそのヘッダを include する他 .c を再コンパイルせず、新旧のレイアウトが混在。
  フィールド offset が食い違い→メモリ破壊→`behaviors[]` 配列外ジャンプ→ハング。切り分けの
  結論は「スロット構成でも SDCC でもなく**ビルドシステム**」だった。→ **各 .rel を全 include
  ヘッダ（`$(HDRS)`）に依存**させ、構造体を触ったら `make clean`。生成ヘッダ
  `assets_data.h` も `HDRS` に含める。
- **常駐 24KB の天井**：rompack が超過をビルドエラー化する。定数の大物（艦データ・BGM・
  ビットマップ・文字列）はバンクへ、常駐は小 RAM バッファ＋`data_read` のみ。実際に常駐が
  逼迫し、撃破!! パネル（574B）・敵機カラー表・艦名/撃沈文をバンクへ退避して捻出した。

### A-2. VDP / スプライト
- **SCREEN5 は 212 ライン → スプライト停止マーカ Y は 216（0xD8）**。208（0xD0）は 192 ライン
  用で 212 では終端にならず、前フレームの古いスプライトが残って画面がゴミだらけになる。
  `vdp_sprite_init` と `vdp_sprite_hide_from` を **両方 216 に統一**。
- **スプライト X/Y は u8**。画面外の負座標は `(u8)` 化で反対端へ折り返す（上方の世界アンカー
  砲塔が海上に幽霊表示された）。→ 描画の可視判定で **x は 0..255、y は −16..212 の外は描かない**。
- **縦スクロール R#23 はスプライトにも効く**。画面固定スプライト（HUD/自機）は Y に
  `g_vscroll(=cam&0xFF)` を加算して打ち消す。**横 HW スクロール R#26/27 はスプライトに効かない**
  ので、背景に乗る砲塔は `x = ax + g_meander` で自前補正（縦は効く＝非対称）。
- **ラスタ競合**：画面最上部の HUD を重い `ent_draw_all` の後に書くと、ラスタが既に上端を
  通過してから属性更新され R#23 とズレて 1px 上下振動する。→ **表示クリティカルな書き込み
  （R#23＋上端スプライト）はフレーム先頭で確定**、HUD は `ent_draw_all` より前に描く。
- **1 走査線 8 枚（V9938 mode2）**。HUD を低 slot に置けば、8 枚を超えても敵機（高 slot）が
  先に間引かれ HUD は残る。
- **スプライトテーブルは page0**。縦スクロールで page0 末尾（Y232–255）が可視域に回り込み
  中央に横帯のゴミが出る。→ スクロール背景は page1 に描き page1 を表示、スプライト表は page0
  のまま非表示にする。
- **文字は BIOS CGTABL に依存しない自前 8×8 フォント**。C-BIOS は CGTABL が不安定で実機とも
  食い違う。BIOS フォント流用は「タイトルとも旧版とも書体が違う」退化になった（0 が丸 o に
  見える等）。→ 自前 fontset を常駐に持ち、テキスト描画と HUD 数字を同一書体で統一。

### A-3. サウンド
- **環状シーケンサの 1 音目スキップ**：「`trem==0` なら *先に* idx を進めてから鳴らす」実装
  なので、再生開始時 idx を `n-1` で初期化しないと最初の tick で 0→1 になり毎回 1 音目が
  欠ける（タイトルで発覚）。melody/bass/drum 全 voice で `idx=n-1`（drum は 15）。
- **`bgm_stop` は noise(C) も消す**。melody/bass だけ消すと直前ドラムの音量が残り「さーー」と
  鳴り続ける（開始カードの無音時に顕在化）。

### A-4. ROM 拡張に伴う番地ずれ
- タイトル YJK 画がバンクを占有し 128KB に空きが無く、**ROM を 256KB（32 バンク）へ拡張**。
  この拡張やグローバル追加のたびに RAM 番地がずれる。→ 検証 poke の前に必ず
  `build/rom.map` / `.noi` で `_g_*` の番地を取り直す（実際に stale 番地でボスを叩いていた）。

### A-5. タイトル（SCREEN12 YJK）
- YJK は 4px を 1 グループ（共有の色差 J,K ＋各画素の Y）で持つ。合成文字（改・KAI）を
  重ねる際は**変更した 4px グループのみ再エンコード**し、原画のクオリティを保つ。原画は
  `assets/title_base.yjk` として固定し、`tools/gen_title.py` が冪等に再生成する。

### A-6. R800 の ROMフェッチ律速と page1 動的RAM実行（§4-3）
turboR の R800 は DRAMモードでも、**カートリッジ(ROM)からのコードフェッチが内蔵RAM実行の約3.8倍遅い**
（実機S1990タイマで実測）。戦闘の処理落ちは最終的にここへ収束し、「常駐ホットコードをRAMで実行する」
のが本命の対策になった。だが MSX 固有の壁がいくつもある。
- **ASCII8バンキングとの衝突**: バンク選択レジスタ(0x6000/0x6800/0x7000/0x7800)は **page1** にある。
  page1 を RAM スロットへ切替えると、その間はバンク切替が書けない（RAMに書くだけ）。→ **ホット区間は
  `data_read`/バンク切替を一切呼ばない**設計にし、`page1_use_ram()`/`page1_use_cart()` で区間を挟む。
  区間内で唯一バンクする `bgm_play`（艦出現時1回）だけ一瞬 cart へ退避する。
- **"足元を切替える"問題**: page1 のコードを実行しながら page1 スロットを差し替えるため、切替ルーチンは
  **page3(RAM)へ退避したコピーから実行**する（`ramexec.c` の blob）。RAM複製は ROM とバイト同一なので、
  切替後も同一番地で実行が継続できる。ENASLT(0x0024)で拡張スロットにも対応。
- **安全側フォールバック**: 空きセグメントが実RAMかを起動時にプローブし、非対応/失敗なら**何もしない
  ＝ROMのまま**（`g_ramx_ok=0`）。C-BIOS(MSX2+)も slot1=cart/slot3=RAM/標準マッパーなので**同じ経路で
  動き、openMSXで正当性検証可能**（速度差はturboRのみ・挙動は不変）。
- **計測知見**: `ent_draw_all` 等が RAM実行化して DRAW 約-2ms、1 VBLANK超フレームが激減（OVER1VB 25→1/60）。

## B. 旧版から移植した部分で、旧版でも苦労した点

移植にあたり、旧版「零の咆哮」で確定していた次の知見を写した。**「旧版に在った機能は、
まず旧版の実装を読み、順序・鳴り物・表示ページ・裏で走る準備まで正確に把握してから作る」**
——これ自体が旧版制作から得た最重要の教訓である（開始カードを旧版を見ずに作り 2 回やり直した）。

### B-1. VDP 書き込みの原子性（＝旧版 shadow-sprite-crash の真因）
- **VDP 操作は「1 操作＝1 つの di/ei 区間」に閉じる**。レジスタ設定（0x99 の 2 バイト）と VRAM
  書き込み（0x98）を細切れの di/ei に分けると、隙間に 60Hz BIOS 割込み（BIOS も VDP ステータス
  を読む）が刺さり、選択・アドレスラッチがずれる。**書き込み回数が多いほど確率的にいつか刺
  さり、固着・スクロール崩壊・一瞬表示→復帰など毎回違う偽バグ**になる。→ 毎フレーム更新
  （スプライト属性＋R#23 等）を全部 1 区間に統合。「2 枚目スプライトが環境の壁」は誤結論で、
  実体はエミュ差でなく BIOS の重さの差だった。
- **`wait_cmd`（VDP コマンド完了待ち）は MSXgl 方式に一致させる**：毎ループ di → S#2 を選び直す
  → R#15 を S#0 へ戻して ei。自己流の `while(CE){}` は R800 でグレーハングする。
- コマンドコード：塗り＝LMMV **0x80**／VRAM 間コピー＝LMMM **0x90**／CPU→VRAM＝LMMC 0xB0／
  バイト塗り＝HMMV 0xC0。**HMMV は G4（2px/byte）ではバイト単位＝縞**になるので塗りは LMMV。

### B-2. スプライト／スクロール
- **sprite MODE2 の R#5（属性テーブル基底）A7–A9 はオフセットでなく AND マスクで 1 必須**。
  怠ると位置・パターンは正常なのに **slot8 以降が slot(N mod 8) の色に化ける**（128B ごとに
  色テーブルがミラー）。
- **横 HW スクロール R#27 は R#26 と逆向き**：`frac=s&7; R#26=(s>>3)+(frac?1:0);
  R#27=(8-frac)&7`。R#25 bit1 で左端 8px のゴミをマスク。
- **入力は GTSTCK 禁止**（BIOS キー走査が割込み依存で、GTSTCK+DI はフリーズ/dir=8 へ流れ続ける）。
  keymatrix を PPI 直読み（選択＋読みの 2 命令だけ短く DI→即 EI）。

### B-3. 炎上演出（本作の常時炎上・撃破スペクタクルの土台）
- **透過 LMMM（0x98）は `wait_cmd` で固着**する環境がある → **背景を先に焼き込んで通常コピー
  0x90 だけで流す**方針にした（本作の火球は「艦バッファ B へ焼き込み→スクロールで流す」）。
- **透過演出の残像**：非 0 画素しか上書きしないため、動く部品が前フレームと違う位置に出ると
  前画素が飛び火する。対策＝毎フレーム同一の「覆う土台」（半径 r の塗り円）を先に描き、動く
  部品を半径 r 以内に収める。火球を**丸く**したのもこの流儀に沿う（四角い塗りは違和感が強く却下）。
- **火球の位置補正**：パターン面 page0 の点 (Px,Py) は画面上で `(Px+weaveX, Py-scrolled)`。
  自機（画面固定）に出すには逆補正。自機死亡時はスクロールをリセットしない（死んだ場所が
  分からなくなる）。※理解するまで爆発位置がズレ続けた。
- **page0＝256 行の回り込み**：艦は 496 行だが page0/リングは 256 行。演出ボックスが上下端を
  跨ぐと mod256 で反対側へ回り込む → スキップせず**ハミ出す行だけ分割してクリップ**。

### B-4. 海／擬似多重スクロール（本作 SEA13 の前提）
- **カラーサイクリング海は不向き**（同じ壁を 2 回踏んだ）：青 3 色パレット回転は「チカチカ」に
  なり、MSX2 16 色が満杯で海地色を回す機構自体が不適。打ち止め。
- **横帯スプリット（R#19 ライン割込）は原理的に無効**：海は左右の縦コラム／艦は全高＝どの
  走査線も艦＋海が混在し、縦コラム分割手段が VDP に無い。→ 成立ルートは案 13＝「in-place・
  海コラムのみ・艦不可侵・跳びを粗ノイズで隠す」＝本作の `sea_frame`。

### B-5. スクロールする大量文字（エンディングのクレジット）
- 毎フレーム直接描くとバースト負荷で処理落ち → 全行を最初に一度だけ画面外バッファへ描き、
  スクロール中は高速 LMMM 1 発で 1 行ずつ流す（`draw_row` と同じ流儀）。

### B-6. SDCC / ROM 配置
- **`_CODE` が `--data-loc` を超える物理衝突**（症状＝スプライト飛ぶ／緑ゴミ／多彩で不安定、
  生成 asm も VRAM も正しいのに）。→ 末端を疑う前に `.map` の `s__CODE`/`s__DATA` を見る。
- **ROM では `_INITIALIZER` を ROM 側へ置かないと初期値付き static が化ける**（const は無事）。
  → 初期値付き static を避け、`init` で実行時に書く。
- **asm からしか呼ばれない関数（ISR 系）は SDCC の未使用除去で消える** → 非 static 化＋`.map`
  で `_xxx` の存在確認。
- **SDCC は同時 1 プロセス厳守**（連投で多重起動→スワップ地獄）。**1 関数が ~400 行/10KB を
  超えると `sdcc -c` が数十分・RSS 数 GB 爆発**（レジスタ割当が超線形）→ 関数分割。
  `long`（32bit）演算は +約 1.7KB になるので 16bit Bresenham で代替。

## C. 検証環境（openMSX headless）の罠

- 検証機は **C-BIOS_MSX2+ ＝ Z80 3.58MHz**（turboR/R800 でない、turboR ROM 未同梱）。速度は
  実機ターゲット（R800）より悲観的。最終的なタイミングは実機で要確認。
- **`puts` は stdout に出ない** → `open ... w` でファイル出力。
- **PSG レジスタの debuggable 名は `"PSG regs"`**（× "PSG registers"）。VRAM は `debug read VRAM`。
- **表示スプライト数を数えるなら停止マーカ（Y=終端値）以降を無視**。全 32 スロット走査は残骸を
  誤カウントする。
- **Tcl ヒアドキュメントで `$i` 等がシェル展開・配列誤認されないよう注意**（アドレスだけシェル
  展開、Tcl 変数はエスケープ）。実際に `#$i(...)` が「配列でない」エラーを openMSX に出した。
- **throttle off は時刻が非決定的**。検証用 insta-clear（無敵）でステージが巡回するため、結果
  画面など単一フレームの撮影は不安定＝各要素は個別に確認する。
- グローバル追加で番地がずれる → 検証 tcl の前に必ず `build/rom.map` で `_g_*` を取り直す。

## D. デバッグ姿勢（横断・最重要）

- **不具合を CPU/エミュのせいにしない**。砲塔が三角・自機暴走・ハングを R800 やエミュのせいに
  してワークアラウンドを積み、堂々巡りで大量のトークンを浪費した。エミュ差/CPU 差に見える
  現象もほぼ**自分のコードが正しい作法を外している**のが真因。
  1. まず自コードの誤りを疑う
  2. 実在の動作コード（Fusion-C, MSXgl, libmsx）と 1 対 1 で突合する
  3. **背理法：市販 ROM が同じ機能で動くなら 100% 自分のバグ**
  4. ワークアラウンドを積む前に、正しい作法を 1 つ見つける
- **サイレント誤変換＝最悪**。未知の値/シンボルを無診断でフォールバックせず、ツール
  （`gen_assets.mjs` 等）は範囲外値を `throw` させる運用にする。

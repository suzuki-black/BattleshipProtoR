# 開発で苦労したこと ― 誤診・地雷・原因究明の記録

このドキュメントは **零の咆哮 改** の開発で踏んだ罠・誤診・遠回りと、そこから得た教訓を
まとめたものです。**次の弾幕縦スクロールSTGで同じ穴に落ちないための資産**として書いています。
（成功した設計は [各処理アルゴリズム解説](アルゴリズム解説.md) 側にあります。）

---

## 1. 起動・初期化・リセット

### 1-1.（最重要）crt0 が BSS(_DATA) をゼロ化していなかった
- **症状**: WebMSX でステージ中に**ソフトリセット**→コナミ→CONFIG→開始 すると、カード表示後に
  ステージが始まらずタイトルへ戻る。表示も崩れる。**クリーン起動では正常**。
- **原因究明の遠回り**: 崩れたのが海帯だったので**最初は自分が入れた YMMM を疑った**（そして念のため
  撤回した）。だが**改修版でも症状が出た**ため YMMM は無罪と判明。次に「リセット後 g_scene が 0x33 の
  ゴミ値」を観測 → **crt0 の gsinit が _INITIALIZER のコピーのみで、未初期化static(_DATA)をゼロ化して
  いない**のが真因だった。初回起動はRAMが0の環境で"たまたま"動き、ソフトリセットはRAMが残るため
  前フレームの state（シーン/フェーズ/画面モード追跡）が残留していた。
- **教訓**:
  - **SDCC ROMプロジェクトでは crt0 に _DATA ゼロ化を必ず入れる**（`s__DATA` から `l__DATA` を0埋め）。
    冷起動と同じ清浄な初期状態を毎起動で保証する。**最初に入れるべき土台**。
  - **表示が崩れた場所＝原因、とは限らない**。状況証拠（海帯＝YMMM）で決め打ちせず、**再現して確定
    させる**。「改修版でも同症状」という切り分けが YMMM 無罪を証明した。

### 1-2. SCREEN12→SCREEN5 復帰で R#25(YJK) が残留し海が白化
- タイトルは SCREEN12(YJK自然画)、ゲームは SCREEN5。BIOS の CHGMOD は V9958拡張の **R#25 を管理しない**
  ため、SCREEN12 の YJKビットが残ると SCREEN5 の表示が壊れる（海が白化）。
- **対策**: `vdp_screen5` で必ず **R#25=0** に落とす。
- **教訓**: 画面モードを行き来する設計では、**拡張レジスタ(R#25等)の残留を明示的に断つ**。

### 1-3. bank シーンの static は 0xE000 共有RAM上で残留する
- CONFIG の `g_mode`(VIEW選択) は bank6 の static で、他のバンクシーン(ship_render等)が同じ 0xE000域を
  使うため**残留値になり得る**。放置すると START時 `g_view=残留` で「カードのみ→タイトル」誤動作。
- **対策**: `config_init` で `g_mode=0` を明示。**バンク共有RAM上の static は入場時に必ず初期化**。

### 1-4.（再発）CHGMOD が VRAMキャッシュ(海テンプレ/艦バッファB)を消し、再構築スキップで海が崩壊
- **症状**: 普通にスタート→やられて GAME OVER →タイトル→**再スタートで海が全面ノイズに崩壊**。再現性あり。
  **実機turboRでのみ発生。openMSX(C-BIOS)では再現しない**。
- **原因**: `scene_video_enter` はタイトル(SCREEN12)→ゲーム(SCREEN5)入場で `vdp_screen5`→**CHGMOD** を実行する。
  **実機turboR BIOS の CHGMOD は VRAM を広く消去し、海テンプレ(0x10000)/艦バッファB(page2/3) まで消す**。
  1周目は消去後に `prerender_ship`(=`scroll_build_sea`+艦描画)が走り再構築されるが、**同一面をやり直すと
  `rendered_stage==curstage` で prerender がスキップ**され、消えたテンプレが再構築されないまま
  `scroll_init` がコピー→海が崩壊。**キャッシュ有効フラグ(RAM)と実VRAMがCHGMODで乖離**する穴。
- **対策**: `stage_init`(タイトル→新規ゲームの唯一の入場点=必ず画面モード往復を伴う)で **`rendered_stage=-1`**。
  入場のたびに CHGMOD 後の再構築を強制する。コストは1周目と同じ艦生成1回のみ(カード表示の裏)。
- **なぜC-BIOSで出ないか**: C-BIOS の CHGMOD は消去範囲が狭くテンプレ領域(0x10000)に届かないため。
  **実機依存バグは C-BIOS 検証をすり抜ける**。BIOS依存(CHGMOD/CGTABL等)の挙動差は常に疑う。
- **教訓(=1-1/1-2 の再発)**: 「一度直したリセット漏れ」と**同じクラス**(状態の残留/乖離)が**別リソース**で再発した。
  1-1 は RAM state 残留、本件は **VRAMキャッシュの有効フラグと実VRAMの乖離**。
  - **BIOS/画面モードをまたぐ操作は、キャッシュしたVRAM資産を無効化してから再入場する**。
  - **「有効フラグ=RAM」と「実体=VRAM」を別々に持つ設計は、両者を同期させる責任を明示せよ**。
    フラグだけ生きて実体が消える経路(CHGMOD/リセット)が必ず穴になる。

## 2. 計測（プロファイル）の落とし穴

### 2-1. static変数/関数のアドレスは毎ビルドで動く
- **地雷**: 検証スクリプトに古い g_scene アドレスをハードコードし、**ゴミ(0xFF=65535)を読んで
  「機械が誤動作」と誤診**した。実際は単にアドレスが移動していただけ。
- **対策**: static アドレスは毎回 `rom.noi`(DEF行)から取り直す。読んだ値が明らかにおかしい時は
  **まずアドレスとスクリプトを疑う**。

### 2-2. Tcl `after time "...[...]..."` は登録時に評価される
- `after time $t "... [debug read ...] ..."` と**二重引用符**で書くと `[...]` が**登録時に評価**され、
  常に開始時刻の値が入る。これで一度「機械がリセットしている」と**誤診**した。
- **対策**: **波括弧か `list`** を使う（`after time $t [list snap $t]`）。**測定結果がおかしいときは
  まず測定スクリプト自身を疑う**。

### 2-3. 単発の遠い after time が発火しない
- 遠い未来の単発 `after time` イベントは確実には発火しない。**0.3秒ハートビートのポーリングループ**で
  待つ。

### 2-4. idle で測ると当たり判定を過小評価
- 自機非発砲だと自機弾が無く collide が軽く見える（13ms）。**発砲中は34msに急増**。
  `keymatrixdown 8 0x01`(SPACE)で**発砲ホールドして実プレイ条件で測る**。安定させるなら
  `g_invinc` を poke して不死化（自機死亡による計測窓ズレを防ぐ）。

### 2-5. シナリオ乱数で±5msのノイズ、小改善は単発では見えない
- 敵撃破数/弾数の乱数でフレーム時間は±5ms揺れる。**数msの改善は単発比較では埋もれる**。
  海間引きの−4msも単発では見えなかった。**構造的に確定する改善（実行回数半減など）は回数ベースで
  確定**させ、フレーム時間の単発比較に頼らない。

### 2-6. openMSX の settings.xml を壊して 0.37×激遅（別プロジェクトも巻き込み）
- **症状**: 別プロジェクトのROMでも激遅。**原因を「CPU負荷」と誤診**した。
- **ユーザ指摘**: 「最新CPU(M5 pro)でCPUが原因の速度低下は有り得ない」→再考。
- **真因**: settings.xml の `samples=64`（既定1024）で throttle が小さな音バッファに同期し 0.37×に
  なっていた。`throttle off` で59×出た＝CPUは無実。
- **教訓**:
  - **openMSXのグローバル設定(settings.xml)を触るときは必ず事前共有**。一時的変更は**起動オプション
    (`-setting <tempfile>`)**で行い、グローバルを汚さない。
  - `throttle off` の実測が「CPU律速か環境要因か」の切り分けに効く。

### 2-7. 微最適化はコンパイラに勝てない
- 当たり判定内側の座標hoist/overlapインライン化を手で入れたが**実測差ゼロ**（sdccが既にCSE/インライン
  済み）。しかもコード増でオーバーフロー誘発 → **revert**。
- **教訓**: `--max-allocs-per-node 3000` の sdcc は既に強力。**手書き微最適化でなく構造的削減
  （走査回数・コピー面積・エンティティ数）**に投資する。

### 2-8.（本セッション最大の誤診）計測画面がゲーム状態(VRAM)を破壊 ― 炎BG文字化けの真犯人はプロファイラ
- **症状**: 戦艦モードで砲台/対空砲を撃破すると、炎上BGがフォント文字に化ける。
- **私の誤診の連鎖（全部ハズレ）**: ①「`burn_bake`が直接VRAM書込だから走行中の海コピーと競合」→ 実は
  透過LMMM(発行前にcmd_wait)で競合しない。②「海の状態機械の二重進行(H-B)/`vdp_fill`のSX/SY残置(H-A)で
  座標化け」→ コードで否定。③「Z80(C-BIOS)で再現しない＝**R800タイミング固有**」→ **これも誤り**。
  ここまでで別AIへの往復まで浪費した。
- **ユーザ指摘で解決**: 「非デバッグROMなら実機で炎は正常」「**あなたのデバッグ処理の方に問題あるのでは**」。
- **真因**: 炎ソースタイルは page0 の y0..31 に置いてある（gameplay中は page1 表示で隠れた保管領域）。ところが
  **DEBUG_PROFの凍結表示(`prof_frame_end`)が page0 を表示に切替え y0..110 を黒塗り＋フォントで上書き**し、
  炎タイルをフォントに化けさせていた。以後 `burn_bake` はその化けたタイルをコピー→炎BGが文字になる。
  `bake_fireballs`はstage開始1回なので、一度凍結表示を出すと次stageまで壊れ続ける（症状と完全一致）。
  Z80で再現しなかったのは**FORCE_KILL版をDEBUG_PROF抜きでビルドした**からで、R800固有だからではない。
- **教訓（§4/§Dの再発を自分でやった）**: **計測器がゲーム状態(VRAM)を破壊していた古典**。「実機だけ」
  「Z80で再現せず」を安易にR800/エミュ固有と決め打ちせず、**まず計測器・デバッグ処理自身を疑う**
  （2-1/2-6と同型）。修正は prof表示を y32以降へ移し炎タイル(y0..31)を触らないだけ（計測ビルドのみ）。

### 2-9. VDP-CPU並列化は「純CPU区間」の裏でだけ（ent_draw_allと重ねてはいけない）
- 炎のVDPコピーを `ent_draw_all` の前へ出して並列化を狙ったら**DRAWが約+1ms悪化**（実測）。`ent_draw_all`は
  SAT/色を**CPUでVRAM直書き**するため、走行中のVDPコマンドと重ねると両者が競合して**双方遅くなる**。
- **教訓**: VDP-CPUオーバーラップ(§4-1)が効くのは**VRAMに一切触れない純CPU(＝AI計算)の裏**だけ。VRAMを
  触るCPU区間とVDPコマンドは重ねない。→ 炎の並列化は撤回し、海(§4-1)はAI計算の裏に限定した。

## 3. VDP・描画の地雷

### 3-1. 撃破!!パネルの文字が潰れる（直書きが60Hz割込と衝突）
- パネルを**per-pixel直書き**すると走行中のVDPコマンドや60Hz割込と衝突して文字が潰れる。
- **対策**: 旧版に倣い **run-length の LMMV(塗り)** で描く（連続ビットごとに vdp_fill）。
- **教訓**: 「できない」で済ませず**旧版ソース/文献を当たる**。直書きは割込と競合する前提で設計。

### 3-2. 炎がリング直blitで256px離れた砲台にエイリアス
- 表示リングは256px周期＜艦496px。炎をリングへ直接blitすると256px離れた砲台に炎が乗る
  （手前を壊すと奥に半分炎）。
- **対策**: 必ず **艦バッファB経由**（draw_rowが行ごとに正位置へ写す）。

### 3-3. u8 スプライトYの折返しで幽霊表示
- スプライトYは u8。世界アンカーの砲台などが画面上方(負のy)にある間に (u8)化で反対端へ折返し、
  海上に幽霊表示される。**y範囲(-16..212)外は描画しない**でガード。

### 3-4. 停止マーカは 216(0xD8)（212ライン時）
- スプライト終端の停止マーカは **212ライン時は216(0xD8)**。208(0xD0)は192ライン用で、212では終端に
  ならず古い残像が残る。

### 3-5. 8フレーム毎の全域再描画で約0.5秒周期のヒッチ
- 炎アニメを「8フレーム毎に全域(14行)一括再描画」にしたら**約0.5秒周期でフレームが停まる**ヒッチが出た
  （ユーザ「一定間隔でフレームが停まる、やり直し」）。
- **対策**: **1件/フレームのラウンドロビン＋コマ変化時のみ**再描画に分散。
- **教訓**: **Nフレーム毎の重い一括処理は周期ヒッチの元**。1件/フレームに分散する。

### 3-6. YMMM は移植性・リセット耐性が低い
- YMMM(0xE0)は速い(64cyc/px)が「DXから画面端まで」で残留VDP状態に敏感。WebMSXのソフトリセット後に
  海帯が崩れた（openMSX/クリーン起動では正常）。効果−0.8msに対しリスクが見合わず**撤回**。
- **教訓**: **効果対リスク（移植性）が悪い命令は使わない**。艦と同じHMMMが安全。

### 3-7. コマンドレジスタの差分発行(§B3)は破綻＝コマンドレジスタは毎回書く
- turboR向けに「コマンドレジスタ(R#32-46)を前回書いた値と比較し、変わった分だけ発行」を試作したが、
  phase1の海(HMMMコピー)が**砂嵐状に破綻**。単一writer＋valid フラグ等の安全策を入れても崩れた。
- **真因**: **V9938/58 のコマンドエンジンはコマンド実行中に SX/SY/DX/DY 等を作業カウンタとして自ら
  書き換える**。ゆえに「前回"書いた"値」と「実行後の実 VDP レジスタ」は一致せず、"変わっていないから
  省略"の判断が誤り、省略したレジスタが化けた値のまま次コマンドが走って破綻する。
- **教訓**: **コマンドレジスタは「発行後に VDP が消費・改変する」前提で毎回書く**。差分発行は読み戻しでも
  しない限り成立しない。YMMM(3-6)と同じ「残留状態依存」の系統。詳細は [高速化の試行記録](高速化の試行記録.md)。

## 4. 誤診しないための姿勢（メタ教訓）

- **「本当にそれが真の原因か？」を疑う**。「海が本当に遅い真の原因か？」というユーザ指摘が
  区間切り分け（VDP律速 vs CPU律速）につながった。
- **測定結果がおかしいときは、まず測定スクリプト自身を疑う**（2-1, 2-2）。
- **状況証拠で決め打ちせず、再現して確定させる**（YMMM無罪の切り分け＝1-1）。
- **できないで済ませず、旧版ソースや技術文献(Grauw/MSX.org/Konamiman)を当たる**。
- **プロトのプロトより劣化させない**。旧版に在った機能は**先に旧版実装を読んでから**作る
  （開始カード＋ファンファーレで2回やり直した）。

## 5. 仕様・移植・進め方

- **明示指示を勝手な解釈で拡張しない**（タイトル表記で叱責された）。要件は文字通り実装する。
- **旧版機能の移植は先に旧版実装を精読**してから（憶測で作ると劣化移植になる）。
- **敵が画面切替で唐突に消える** → `ent_clear` で瞬間消去せず**自然に飛び去らせる**（spawnゲートで
  新規湧きは止まるので艦の上に湧く心配はない）。
- **入力再現の罠**: コナミの最終キー A(TRIG) は、タイトルでは**ステージ開始も兼ねる**ため、
  リセット後の自動再現でステージが始まってしまい再現がずれた。
- **高速化で"速すぎて遊べなく"なった（フレームレート依存の罠）**: ゲーム速度(敵速/弾速/スクロール/
  spawn/アニメ)が**すべてフレーム数指定＝フレームレート依存**だったため、§4-1/§4-3で60fps化した瞬間に
  **全部が2倍速**になった。対策は固定タイムステップ（ステージのみ2 VBLANK待ち＝安定30fps）。速くする
  前に「その速度はフレームレートに依存していないか」を意識する。60fpsで遊ばせたいなら全速度定数を1/2へ。

## 6. 音

- **bgm_stop で chC(noise) も消音**しないと、直前のドラム音量が残り「さーーー」とノイズが鳴り続ける
  （開始カードで顕在化）。melody/bass(chA/B)だけでなく **noise(chC)も明示的に0**にする。
- **効果音がメロディを消す（メロディ死守）**: 自機発射音/被弾音を **tone A(メロディと同じch)** で鳴らして
  いたため、撃つ/被弾のたびにメロディ(A)が譲って消えていた。自機は撃ちっぱなし＝**全ステージで発生**
  （3面で目立って気づいた、が実態は全面）。PSGは3chしか無く効果音は必ず1ch奪うので、**発射音/被弾音を
  ベース側(tone B)へ移し、メロディ(A)は効果音に一切譲らない**設計へ（ベース/ドラムが譲る）。★"どのchを
  犠牲にするか"は音楽上の優先度で決める＝**メロディ最優先**。

## 7. openMSX 運用ルール（複数プロジェクト同時進行）

- **`pkill -f openmsx` を使わない**。別プロジェクトの計測実行を巻き込んで壊す。後始末は
  **自分のセッションのスクリプトパス（スクラッチのセッションUUID）で絞る**
  （`pkill -f "<session-uuid>"`）。
- 計測スクリプトはスクラッチディレクトリに置く（`-script` のパスにUUIDが入り絞り込みが効く）。
- **`timeout` を必ず付けて起動**（`exit` に到達しなくても置き去りにならない）。
- **グローバル設定(settings.xml)の変更は事前確認**。一時変更は起動オプションで。

## まとめ（次作への一行教訓）

1. **crt0 で _DATA を必ずゼロ化**（リセット残留state対策）。
2. **アドレスは毎ビルドで動く**。おかしい値はまずアドレス/スクリプトを疑う。
3. **実プレイ条件（発砲ホールド＋不死poke）で測る**。idleは過小評価。
4. **微最適化でなく構造的削減**（走査回数・コピー面積・エンティティ数）。
5. **VDP律速は塗る頻度・面積を減らす**（方式高速化だけでは足りない）。
6. **効果対リスクの悪い命令(YMMM等)は使わない**。
7. **Nフレーム毎の一括処理は周期ヒッチの元** → 1件/フレームに分散。
8. **状況証拠で決め打ちせず再現して確定**。測定スクリプトを疑う。
9. **旧版/文献を当たる**。「できない」で止めない。
10. **openMSXはUUIDで絞る・timeout必須・グローバル設定は事前確認**。

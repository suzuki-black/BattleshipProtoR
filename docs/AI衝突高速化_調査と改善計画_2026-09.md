# 多スプライトMSXの AI・当たり判定 高速化：調査と本プロジェクト改善計画

対象: BattleshipProtoR（MSX turboR 専用 縦STG, SDCC/Z80命令, R800 DRAMモード実行）
前提資料: `turboR性能調査報告_2026-09.md`, `R800_ROMFETCH_AND_LOGIC_PLAN.md`
本資料の位置づけ: 「非高速モードの素のMSXゲームができている多スプライト表示が、なぜキャラの少ない turboR 専用機で
アルゴリズム起因で低品質になるのか」を、**一次情報（msx.org開発板・Grauw・ARTRAG/Uridium・Transball）** と
**本コードの実測（生成asm）** の両面で確定し、効果順の改修計画に落とす。

---

## 0. 結論（先に4行）

1. 律速は VDP でなく **AI/発砲/当たり判定のCPUコスト**。しかも「コードをどこで実行するか(ROM/RAM)」でなく **アルゴリズムと8/16bitの選択** が主因。
   （本セッションで実証: 当たり判定のRAM化=速度不変、AA走査のRAM化=微増だが窓化での走査削減=不変 → 走査数でなく**演算の中身**が重い）
2. 素のMSX(Z80 3.58MHz)でも Transball は **敵32・弾4/4・爆発2・タイルアニメ64** を滑らかに回せている（santiontanon実測）。
   本作は同規模以下なのに重い ＝ **1オブジェクトあたりのコストが過大**。
3. 本コードの過大コストの正体（生成asmで確認）:
   **(a) 弾ごとに16bit乗算×2＋符号付き除算×2（`emit`）** / **(b) 狙い弾ごとに内積~30回（`aim_dir`）** /
   **(c) 毎フレーム プール全走査 約6回(各O(30))** / **(d) 全座標がs16=全演算16bit**。
4. Grauw ら一次情報の総意 ＝ **「命令エンコード(IX→HL等)より先にアルゴリズムを削れ：対象限定・思考間引き・事前計算・8bit化」**。
   本作の改善順もこれに従う（§4）。RAM実行化は turboR で有効な"最後の一押し"だが、上記を削ってからでないと薄まる。

## 1. フレーム予算（なぜ数千サイクルの無駄が効くか）

- NTSC 60Hz 実機 Z80 3.579545MHz ＝ **約 59,700 T-state/フレーム**。
- MSXは **M1サイクルごとに+1ウェイト**が入り、命令の実効は公称より重い（Grauwの表はこのM1込み）:
  `ld a,(hl)`=8T / **`ld a,(ix+o)`=21T** / `add hl,de`=12T / `inc l`=5T / `djnz`=14|9T / `call`=18T / `sbc hl,de`=17T。
- **16bit乗算(`__mulint`)≈ 数百T、符号付き16bit除算(`__divsint`)≈ 数百〜千T**（Z80に乗除算命令が無くライブラリ呼び）。
  → 弾1発の速度計算(乗2+除2)だけで**千T級**。弾を毎フレーム十数発扱えば **1〜数万T = フレームの数十%** が消える。
- turboR R800 は速いが、**カートリッジROMのコードフェッチにウェイト**（内蔵RAMのみ高速）。乗除算ライブラリはROM常駐なので
  R800でも遅いまま。→ だから「behaviorをRAM化しても不変」だった（時間はROM側の乗除算/callee に在る）。

## 2. 本コードの実測ボトルネック（生成asmで裏取り済み）

全体で **`__divsint`×16箇所 / `__mulint`×14箇所** のライブラリ呼び（多くが `fire.c` のホットパス）。

### (a) 弾ごとの16bit乗算＋符号付き除算 — `src/core/fire.c` `emit`/`emit_burst`
```c
b->vx = (s16)dvx[dir] * spd / 8;   // __mulint + __divsint
b->vy = (s16)dvy[dir] * spd / 8;   // __mulint + __divsint
```
弾を撃つ**たびに乗2+除2**。`/8` は符号付きなのでシフトに落ちず `__divsint`。**最有力の無駄**。

### (b) 狙い弾ごとの内積 ~30回 — `fire.c` `aim_dir`
`dx*dvx[i] + dy*dvy[i]` を粗8方向＋密7方向 ≈ 15方向 → **`__mulint` 約30回/狙い弾**。砲台/AIが同時に狙うとスパイク。
（旧版64回→30回に半減済みだが、それでも乗算そのものが残っている）

### (c) 毎フレーム プール全走査 約6回（各 O(ENT_MAX=30)）
`ent_recount_ebul` / `ent_update_all` / `ent_resolve_collisions`(分類) / `aa_collide`(自機弾収集) / `fire_draw` / `ent_draw_all`
＝ **約180反復/フレーム** を「実処理の前の走査」に消費。古典ゲームは**アクティブリスト1回**で済ませる。

### (d) 全座標が s16（16bit）
`Entity` の `x,y,vx,vy,ax,ay` が全て s16 → 移動・比較・当たりの**全演算が16bit**（`add hl,de`=12T, `sbc hl,de`=17T）。
素のMSXゲームは**8bit画面座標**が定石（`add a`=5T, `cp`=5T ＝ 1/3以下）。

### 既に手当て済み（評価のため明記）
- 当たり判定は既に **対象限定**（自機弾×敵 / 脅威×自機）＋ **X軸早期棄却**＋overlapインライン＋弾座標ホイスト（`ent_resolve_collisions`）。
- 敵弾数・生存砲台は **O(1)カウンタ**（`g_ebul`/`g_lturret`）。
- 描画は `__naked` ASM（`draw1`）。AA/behavior は RAM実行（turboRのROMフェッチ回避）。
→ **残るはアルゴリズム核**：乗除算の事前計算化・思考間引き・走査統合・8bit化。

## 3. 外部の定石（一次情報。各項に出典）

### 3-1. オブジェクト管理：256整列SoA / H=フィールド・L=ID
[z80 speedup by struct of arrays](https://msx.org/forum/development/msx-development/z80-speedup-struct-arrays-8bit-style)（ARTRAG/PingPong/Grauw等）。
各フィールドを256整列配列に置き `ld h,フィールド / ld l,id / ld a,(hl)`(8T) で読む。フィールド切替=`inc h`(5T)。
**効果は限定的**（実測 IX版99T vs HL版96T＝数%）。真価は記述性とランダムアクセス削減。RAM浪費(256×N)がトレードオフ。
→ **本作では優先度低**（数%）。Grauwの助言どおりアルゴリズムが先。

### 3-2. 座標は8bit・画面座標で判定
santiontanon(Transball): 当たりは**画面座標**で取る（見た目と一致）。位置は `整数8bit + 小数8bit` の固定小数、判定は整数8bitのみ。
16bit演算/ライブラリ呼びを避けるのが動機。出典 [Arcade shooters…Logic](https://www.msx.org/forum/msx-talk/general-discussion/arcade-shooters-on-the-z80-machines-logic)。

### 3-3. 当たり判定
- **Grauw定式**: `abs(a.center-b.center) < (a.extents+b.extents)` を各軸。ペアが固定なら **extents和を事前計算**。
  出典 [Rectangle Intersection Z80](https://www.msx.org/forum/msx-talk/development/rectangle-intersection-z80-machine-code-implementation-any-tips)。
- **ARTRAG Uridium `collision_tst.asm`**: **1軸8bitで先に早期棄却（Yで弾く→Xへ）**、約24〜35T/軸。非アクティブは`bit`で飛ばす。
  出典 [Uridium-msx1](https://github.com/artrag/Uridium-msx1/blob/master/collision_tst.asm)。
- **対象を方向限定**（自機弾×敵、敵弾×自機のみ。敵同士は判定しない）＝O(n²)を排除。
- **カスケード**: 円/正方の粗判定→通過時だけ厳密。円は `squares[256]` テーブルで乗算回避、半径和²も事前計算。

### 3-4. AI/思考の間引き（多数の敵を出す最大の鍵）
[Arcade shooters…Logic]:
- Metalion: ISRタイマ0-60の剰余で **スクロール/敵移動/別処理をフレームまたぎで時分割**（「Konamiは賢い」）。
- 定石: **移動は毎フレーム・思考は数フレームに1回**（ID剰余 `id%4==frame&3` 等）、**画面外の敵は思考スキップ**、状態機械はテーブル駆動。
- 効果: 思考を1/4に間引けば思考コスト実質1/4。**多数敵で最も効く**。

### 3-5. 弾/spawn
- 空きスロットのO(n)全走査を避ける: **フリーリスト/空きIDスタック（生成pop・破棄push＝O(1)）**、または **アクティブID詰め配列＋swap-remove**。
- santiontanon実測の**目安**: 弾4/4・爆発2・敵32・タイル64 で滑らか（＝素のMSXで回る現実的上限）。

### 3-6. Z80/R800×SDCC
- SDCCのIXフレーム(`ld a,(ix+o)`=21T)はホット部で不利 → `__naked`＋HL索引で20〜40%（Micha/OOスレ実測）。
- 乗除算はライブラリ呼び → **事前計算テーブル/シフト加算/8bit化で回避**。
- turboR: `MULUB/MULUW` のハード乗算あり（ただしSDCC z80backendは使わない）。**ホットコード/弾ルーチンを内蔵RAMへ**（ROMフェッチ回避）。
  GhostwriterP: 弾のような大量小型ルーチンは **RAM常駐＋変数を即値埋め込み(自己書換)** が turboR で特に有効。
- **Grauwの総意（最重要）**: 「IX/IYを削るより、実行頻度を下げる/索引構造/事前計算/比較削減/柔軟性を捨てる＝**アルゴリズムで稼げ**」。

## 4. 本プロジェクト改善計画（効果の大きい順）

各項: 何を / なぜ効く / 想定効果 / リスク・工数 / 検証法。★=推奨着手順。

### ★A. `emit`/`emit_burst` の速度計算を事前計算テーブル化（乗除算の撲滅）
- **何を**: `dvx[dir]*spd/8` を、使用する speed 値ごとの `s8 vel[spd][dir]`（またはdir→(vx,vy)対）を**起動時に1回**焼いてlookupに置換。
  最低でも `/8`(符号付き除算=`__divsint`)を `>>3` へ（負値の丸めが±1違うだけ＝弾速に無害）＝除算即撲滅。
- **なぜ**: 弾ごとの `__mulint`×2＋`__divsint`×2 → **テーブル読み2回**。弾多発フレームで千〜数千T/frame削減。
- **効果**: 大（本作で最も直接的）。**リスク小**（挙動ほぼ不変、要スナップ確認）。工数小。
- **検証**: openMSXで弾の軌道が従来と一致（screenshot/座標ログ）。

### ★B. 思考のフレーム時分割（移動毎フレーム／思考は間引き）
- **何を**: `run_fire`（＝`aim_dir`＋`emit`の発生源）と敵AIの「発砲・行動決定」を **ID剰余 or フレーム剰余で 1/2〜1/4** に。
  移動(座標更新)は毎フレーム維持。画面外エンティティは behavior 冒頭で可視判定→思考スキップ。
- **なぜ**: `aim_dir`(内積~30)や `run_fire` 解釈の**呼び出し頻度そのもの**を下げる＝乗算コストが線形に減る。多数の敵/砲で最大効果。
- **効果**: 大。**リスク中**（発射レート/難易度バランスが変わる＝要調整。発射間隔で辻褄合わせ）。工数中。
- **検証**: 実機FPS＋弾幕密度の体感。

### ★C. `aim_dir` のテーブル化（内積→8方向オクタント＋比率表）
- **何を**: `atan2`相当を **dx,dyの符号でオクタント決定→|dy|:|dx|比を小テーブルで角度に**（乗算ゼロ）。
- **なぜ**: 狙い弾ごとの `__mulint`~30 を**表引き数回**へ。
- **効果**: 中〜大（狙い弾が多い面で効く）。**リスク中**（狙い角の量子化差＝散らし乱数に吸収されやすい）。工数中。
- **検証**: 同一状況で発射方向が旧版と近いこと。

### D. 毎フレーム プール全走査の統合（アクティブリスト化）
- **何を**: 毎フレーム先頭で **生存インデックスの詰め配列 `g_active[]`** を1回生成し、recount/update/衝突/aa_collide/fire_draw/draw は
  これを回す。死亡はswap-remove。順序依存は「次フレームから」に統一。
- **なぜ**: 約6×O(30)=180反復/frame → 実質 O(生存数)。海/接近フェーズや過疎時に特に効く。
- **効果**: 中（過疎時大・混雑時は生存数≈30で頭打ち）。**リスク中**（多数箇所の走査を差し替え＝stale/順序バグに注意）。工数中〜大。

### E. 8bit画面座標化（弾・当たりの16bit撲滅）
- **何を**: 弾/敵の判定を **8bit画面座標＋8bit小数** に。当たりは Uridium 方式の **1軸8bit早期棄却** に統一（ホット部 `__naked`）。
- **なぜ**: 移動・比較の全16bit演算(`sbc hl,de`=17T)を8bit(`cp`=5T)へ＝1/3。
- **効果**: 中〜大（全エンティティに効く）。**リスク大**（座標系の広範な変更＝スクロール/世界座標との整合。段階導入必須）。工数大。

### F. turboR: 事前計算テーブルと弾ルーチンも内蔵RAMへ（枠を空けてから）
- 現状 page3 RAM枠はほぼ満杯。§A/§Dでコード量が減った後、`emit`/衝突を RAM実行へ（ROMフェッチ回避の最後の一押し）。
  さらなる拡大は マッパーRAM(pages1/2)実行（§2-2）＝turboR固有で openMSX 検証不可＝高リスク。

**推奨着手順: A → B → C → D →（必要なら）E/F。**
A/B/C は「乗除算と呼び出し頻度」を直接削り、リスクが比較的低く、openMSX(Z80)で正当性検証可能。
E は最大級だが座標系の広域改変なので最後。

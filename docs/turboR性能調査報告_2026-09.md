# turboR 性能調査・高速化セッション報告（2026-09-05）

このセッションで判明した性能の実態・実施した最適化・出してしまった不具合・計測手法の
失敗と教訓・残タスクをまとめた**引き継ぎ報告書**。次セッションはここから再開すること。

---

## 0. 要約（結論）

- **実機turboRの実FPSを初めて画面計測できるようにした**（`DEBUG_FPS` ビルド）。結果、
  **海モードで約30fps（60未達）**。「空フレーム（エンティティ処理を全停止）」では **60fps張り付き**。
- 切り分けの結果、**フレーム負荷の主犯は「エンティティ処理（AI＝更新／AA走査／衝突）」**。
  海コピー（VDP）や描画（スプライト）ではない。
- **海モードは敵が数個しか居ないのに30fps** ＝ エンティティ数に比例しない**固定オーバーヘッド**
  （毎フレームの複数のプールO(30)走査＋`aa_update`のO(23)走査）が効いている可能性が高い。
- **最有力仮説: R800のカートリッジROMコードフェッチ・ウェイト**。本作のコードはROM(0x4000〜)上で
  実行され、R800でもコードフェッチはROM律速（`sys.c`のコメント通り）。DRAMモードはRAMデータ
  アクセスしか速くしない。→ **エンティティ処理コードがROMフェッチで律速**しているなら、
  「命令削減」より「**ホットコードをRAMへ配置**」が本丸になりうる（要検証）。
- ★**このセッションのユーザ指摘の核心**: 「AA走査そのものの効率化（全体負荷の大部分）」が目的。
  海モードだけ`aa_update`をスキップするのは対症療法で本質でない。**AA走査・エンティティ処理を
  根本から軽くする**（走査回数削減・データ構造・RAM配置・アセンブラ）のが次の課題。
- ★**担当（私）の反省**: 「無駄は取り切った」という誤った論調で、実際は無駄が全く取り切れていない。
  加えて計測ミス・不具合を複数出した（§5, §6）。

## 1. 実測した性能（実機turboR / openMSX）

計測は `DEBUG_FPS` ビルドの画面FPS（校正済み）と、JIFFY非依存のフレームカウンタで実施。

| 条件 | 実機turboR | openMSX(C-BIOS=Z80) |
|---|---|---|
| 海モード 通常（全処理ON） | **約30fps** | 約21〜26fps |
| 海モード エンティティ処理OFF（空フレーム） | **60fps張り付き** | 60fps |
| 海モード AI（更新/AA/衝突）OFF | 約60fpsへ跳ね上がり | 約30〜35fps |
| 海アニメ（sea_frame）OFF | 30fps（≒通常＝**海は主犯でない**） | 21→23（ほぼ不変） |

**解釈**:
- 空フレームが60fps＝スクロール／HUD／`vdp_wait_frame`等の固定費は軽い。
- **AIを止めると60fpsへ跳ねる＝AI（更新/AA/衝突）が主犯**（実機で確定）。
- 海モードは敵数個なのに30fps＝**エンティティ数に依らない固定的な走査コスト**が主。
- Z80(openMSX)では個別AI差は誤差程度＝**実機turboRでしか正しく切り分けられない**
  （R800はCPUが速くVDPやROMフェッチの相対比が変わるため）。

## 2. 負荷の内訳（毎フレームの処理／未完の切り分け）

`stage_update`（phase0=海モード）が毎フレーム呼ぶ主な処理：

- `ent_recount_ebul()` … 敵弾数の数え直し（O(30)全走査）
- `ent_update_all()` … 全エンティティのbehavior（O(30)。砲台4基は画面外でも`bh_turret`が走る）
- `aa_update()` … **対空砲23基を毎フレーム走査**（`SHIP_NAAG=23`）。海モードでは全AA画面外で
  全部cullされる＝**丸ごと無駄**。phase1では画面内AAが発砲。
- `special_update()` … phase1のみ（海モードは即return）
- `ent_resolve_collisions()` … プールO(30)走査＋自機弾×ターゲットのペア判定
- `aa_collide()` … 自機弾収集（O(30)）＋可視AAとの座標判定
- `ent_draw_all()` … プールO(30)走査＋スプライトSAT/色書き込み

→ **毎フレーム O(30)級の全走査が5〜6回＋O(23)のAA走査**が固定で走る。海モードの30fps
（約33ms/frame）はこの固定走査群がR800でも重い、が実態に近い。

**未完**: AI内訳（AA／更新／衝突のどれが最重か）の実機切り分けは**未実施**。
`DEBUG_FPS` ビルドの MASK 2(=AA停止)/4(=更新停止)/8(=衝突停止) を実機で個別に見れば確定する
（§7の手順）。openMSXでは個別差が誤差で判定不能だった。

## 3. 実施した最適化（コミット済み・効果は原則openMSX実測）

| コミット | 内容 | 効果 |
|---|---|---|
| `a040886` | 当たり判定 `ent_resolve_collisions` の内側ループを `overlap()` インライン化＋弾座標ホイスト＋X軸早期棄却 | collisionブロック **-31.6%**（openMSX, 最悪ケース） |
| `f0ddcce` | 敵弾上限チェック `ent_enemy_bullet_full` と生存砲台数 `ent_live_turrets` を O(1) カウンタ化（発砲ごと/毎フレームの O(30) 全走査を排除） | cap判定 O(30)→O(1)=**17倍**（openMSX） |
| `4e8a73e` | 描画最ホットパス `draw1` を `__naked` ASM 化（eをIY固定でフィールド直読み＝SDCCのスタック往復を排除） | drawブロック **-15%**＋常駐32B減（openMSX） |
| `644c0f2` | （高速化前の実バグ修正）同一面リスタートの海崩壊＋GAME OVER等の右寄り | バグ修正 |

**当たり判定の内訳（openMSX実測, 25体）**: 走査8.4% / ペア処理91.6%。
「走査統合」は低価値と確認（＝正しい判断）。

**重要な知見（[[framework-foundation]]にも記録）**:
- **C-levelの手動hoist/インラインはSDCCの最適化に勝てない**（当たり判定で実証）。
- **が、ポインタ多用のホット関数はSDCCが構造的に非効率コード（Entity*をレジスタ保持できず
  pop/push往復）を吐くので、`__naked`全ASM＋IYオフセット直読みなら大幅に勝てる**（draw1で-15%）。
  → **AA走査・エンティティ処理の残り最適化も、まず生成ASM(build/*.asm)を精読**して
  SDCCの無駄（IXフレーム／スタック往復／乗算）を特定し、必要なら__naked ASM化する方針。

## 4. デバッグ機構（今セッションで追加。すべて `#ifdef DEBUG_FPS`＝リリースは完全に消える）

- `make clean && make DEBUG_FPS=1` … 画面にFPS常時表示のデバッグROMを生成。
  通常 `make` はFPSコード・スプライトslot予約が一切入らず挙動・常駐サイズ不変。
- **画面表示**: 上=FPS(2桁, JIFFY増分を起動時校正した実FPS) / 下="MASK nn"(現デバッグマスク)。
- **M(TRIGB)キー**でマスクをプリセット巡回: `0,2,4,8,16,14,1,31`。
  bit1=海 / bit2=AA(aa_update+aa_collide) / bit4=更新(ent_update_all+special) /
  bit8=衝突(recount+resolve) / bit16=描画。`DBG_ON()`マクロで各処理を個別ゲート。
- 関連コミット: `4116510`(FPS表示) `93f2ed8`(JIFFY校正) `3fbf7aa`(表示ドロップ修正)
  `9abd3f7`(NOSEA) `608db6b`(NOENT) `9a0d2c4`/`95ffbe2`/`bea4e48`(マスク細分化・文字表示)。

## 5. 不具合を出して撤回／中断したもの

- **OTIR化で自機影が"分身"（実機turboR固有）→撤回**（`b337e9d`→`9a3cdf0`）:
  SATバースト `vdp_sat_flush` を OTIR(21T/byte)化したら実機turboRで影が分身。真因＝
  **R800は 0x98(VDPデータ)への連続書込みが速すぎるとV9958のVRAMアクセス窓に追いつかず
  書込み欠落**。Cループは1バイトあたり命令数が多く自然にペーシングされ安全。openMSX(Z80)は
  十分遅く再現せず、実機依存バグがすり抜けた。**教訓: 0x98への一括転送をOTIR/OUTIで速くしない**
  （0x9B宛のレジスタ間接=vdp_cmd_flushは可）。得ていたdraw -7.6%は放棄。

- **spawn探索ヒントを"遅い"と誤判定して棄却→実は速い（未実装のまま）**:
  当初「別replica比較」で hint=36 vs walk=27 として棄却。後日**同一ビルド内A/Bで測り直すと
  hint=19 vs walk=29（-34%）でhintが速い**＝**正しい最適化を誤って捨てていた**。
  ※純走査コスト。実spawnは初期化が支配的なので総効果は小さめだが「遅い」は誤り。**未実装**。

## 6. 計測手法の失敗と教訓（最重要・再発防止）

このセッションは**計測ミスを複数出した**。原因と対策：

1. **ステージ1 vs 2 の比較が、実は 1 vs 1 だった**:
   `g_stage_sel` を起動直後(t=2s)にpokeしたが **crt0のBSS初期化(_INITIALIZER copy)に上書き**され、
   両方ステージ1をロード（結果がビット完全一致だったのが兆候）。
   → pokeは crt0 完了後かつ stage_init 読取り前に行い、**必ず読み戻して検証**。

2. **FPSカウンタが実機で誤値（2〜5と表示）**:
   「JIFFY(0xFC9E)が1VBLANK=+1」前提で 60カウント=1秒 としたが、**実機turboRではJIFFY増分が
   1でないらしく換算が狂った**。openMSXはJIFFY=60Hzで偶然正しく見え、すり抜けた。
   → **起動時にJIFFY増分を実測校正**（`93f2ed8`）。JIFFY非依存のフレームカウンタも併設。

3. **FPS表示が画面上で壊れていた（1走査線8枚制限）**:
   FPS桁をスコア/残機と同じ最上段の走査線に置き、**V9938の8枚/走査線制限で桁がドロップ**。
   `peek`で内部値だけ見て「直った」と繰り返し、**ユーザが見る実画面を確認していなかった**。
   → **別走査線へ分離**（`3fbf7aa`）。**教訓: 内部値(peek)でなくユーザが見る実描画・実挙動で検証する**。

4. **鉄則（[[framework-foundation]]に記録済み）**: 最適化の効果測定は
   **「同一ビルドに新旧両方を入れ、同じ入力で連続測定(A/B)」**。別ビルド比較(mtime stale)・
   別replica比較(実物と差異)・poke(上書き/レース)は誤りの温床。
   **測定値が"完全一致/直感と真逆"なら測定自体を疑え**。

## 7. 残タスク・次の狙い（優先順）

1. **AI内訳の実機切り分け（未完）**: `GAME_DEBUG_MASK.ROM` の海モードで MASK 2/4/8 を個別に見て、
   AA走査・更新・衝突のどれが最重かを確定する。**ユーザ指摘の本命は AA走査（`aa_update`）**。

2. **AA走査（`aa_update` / `aa_collide`）の根本改善**（全体負荷の大部分の疑い）:
   - 現状**毎フレーム23基を無条件走査**。海モードでは全AA画面外で全て無駄。
   - phase1でも23基を毎フレーム舐める（可視AAリスト化で当たり判定側は半減済みだが走査自体は残る）。
   - 案: 画面内AAだけを持つコンパクト表を維持／艦の画面内Y範囲から走査範囲を限定／
     生成ASM精読で走査ループの無駄を削る／ホットならRAM配置。

3. **毎フレームのプールO(30)全走査の削減**（recount/update/collision/aa_collide/draw で複数回）。
   構造的にプールを1回で分類して使い回す等（順序依存に注意）。

4. **★仮説検証: R800 ROMコードフェッチ律速**:
   海モードが敵数個で30fps＝コード量（固定走査）がROMフェッチで律速の疑い。
   検証案: ホットな1関数をRAMへ配置して実機FPSが上がるか見る。上がれば**ホットコードのRAM配置**が
   最大レバー（DRAMモードの真価を出す本丸の大改造）。`sys.c` は現状コードをROMに置いたまま。

5. **未実装で保留**: spawn探索ヒント（-34%走査, §5）。効果は小だが安全。
